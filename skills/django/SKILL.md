# Django on PostgreSQL: transactions, migrations and bulk operations

Verified against Django [6.1.2](https://github.com/django/django/tree/6.1.2) source and identical on 5.2.17. Transaction and migration-transaction rules were reproduced on psycopg2 2.9.13 and psycopg 3.3.6 against PostgreSQL 16.15 and 18.6; the schema-change, bulk-operation and isolation-level rules on PostgreSQL 18.6 with Django 6.1.2 and psycopg 3.3.6. The SQL was read from PostgreSQL's statement log. Line-level source links, logged SQL and diagrams are in `references/`.

## Transaction rules

01. Autocommit is on by default. `AUTOCOMMIT` defaults to `True` and Django applies it to every new connection, overriding PEP 249's "initially off". Outside `atomic()` each statement commits on its own, and neither driver holds a transaction open between queries. `connection.cursor()` never starts or ends a transaction.
02. Use `transaction.atomic()` whenever several writes must succeed or fail together. Entering the block sends nothing; `BEGIN` goes out with the first query inside it, and leaving it sends `COMMIT`, or `ROLLBACK` if an exception leaves it.
03. A nested `atomic()` is a `SAVEPOINT`, released on success. Nothing is durable until the outermost block exits; if it fails, the inner work is rolled back with it.
04. To survive an error and carry on, wrap only the risky statement in its own `atomic()` and catch the exception **outside** it. Django sends `ROLLBACK TO SAVEPOINT` and the outer transaction stays usable.
05. Never catch a database error inside `atomic()` without an inner block. The next ORM query raises `TransactionManagementError: An error occurred in the current transaction. You can't execute queries until the end of the 'atomic' block.`; a raw cursor gets PostgreSQL's `current transaction is aborted, commands ignored until end of transaction block`. The whole block rolls back.
06. Catching the exception tells PostgreSQL nothing. The server keeps the transaction aborted (`idle in transaction (aborted)`) until it receives `ROLLBACK` or `ROLLBACK TO SAVEPOINT`, answers `COMMIT` with `ROLLBACK`, and discards the statements that succeeded earlier in it.
07. `atomic(savepoint=False)` creates no savepoint, so an error inside it dooms the whole outer transaction even if caught. `atomic(durable=True)` raises `RuntimeError` when nested; use it where the code must commit when the block ends.
08. Run side effects (emails, job enqueues, calls to other systems) through `transaction.on_commit(fn)`. It runs after the outermost block commits, never after a rollback.
09. `ATOMIC_REQUESTS = True` makes every view one transaction, so every `atomic()` in view code is a savepoint and nothing commits until the view returns. A job enqueued during the request can start before the commit and miss its rows; enqueue it in `on_commit`. Management commands, `migrate` and workers don't get this wrapper.
10. Django opens transactions for you in `get_or_create()`, `update_or_create()` and `save()` on models with parents. `select_for_update()` outside a transaction raises `TransactionManagementError: select_for_update cannot be used outside of a transaction.`
11. A `select_for_update()` lock lasts until the outermost `atomic()` block ends, not until the query returns. Put the whole read-decide-write sequence in one `atomic()`, keep it short, and do no slow I/O inside it, because every other writer of those rows waits. At `READ COMMITTED`, the default, read, compute, `save()` with no lock loses concurrent updates; when the new value is an expression, `filter(...).update(balance=F("balance") - 30)` avoids both the lock and the lost update.
12. `select_for_update(nowait=True)` fails at once instead of waiting; `skip_locked=True` leaves locked rows out (work queues); `of=("self",)` stops `select_related()` from locking the joined rows too; `no_key=True` doesn't block inserts of rows that reference the locked one. The lock is taken when the queryset is evaluated. Lock several rows in a consistent order (`order_by("pk")`) to avoid `deadlock detected`.
13. Set an isolation level with `OPTIONS["isolation_level"]` to a psycopg `IsolationLevel` (or its integer); a string raises `ImproperlyConfigured: Invalid transaction isolation level serializable specified. Use one of the psycopg.IsolationLevel values.` At `REPEATABLE READ` or `SERIALIZABLE`, a concurrent write raises `django.db.utils.OperationalError` (cause `psycopg.errors.SerializationFailure`, SQLSTATE 40001) instead of losing an update, possibly when leaving `atomic()`; retry the whole block.
14. Don't call `set_autocommit()` in application or migration code. Inside `atomic()` it raises `TransactionManagementError: This is forbidden when an 'atomic' block is active.` If you must, restore the value `get_autocommit()` returned before, never a hard-coded one.
15. With autocommit off, `atomic()` cannot commit: even the outermost block only creates a `SAVEPOINT`, so its work is lost when the connection closes. This holds after `set_autocommit(False)` and with `"AUTOCOMMIT": False`, where even a first `SELECT` opens a transaction that stays open until you call `commit()` or `rollback()`. Keep `AUTOCOMMIT` at `True`.

## Migration rules

16. With the default `atomic = True`, one transaction wraps the whole file: every operation plus the `django_migrations` INSERT, committed together; any failure rolls all of it back. When operations queue deferred SQL (foreign keys and indexes from `CreateModel` or `AddField`), the INSERT runs right after `COMMIT` instead.
17. The row is written only after every operation succeeded. `Applying <app>.<name>... OK` is printed after the INSERT is sent, not after it commits.
18. With `atomic = False` each statement commits as it runs. A failure leaves earlier operations applied and no row, and the rerun fails on "already exists". Keep non-atomic migrations to the operations that need it, make every statement idempotent (`IF NOT EXISTS`, `IF EXISTS`), and put ordinary schema changes in a separate atomic migration.
19. `RunPython(..., atomic=True)` gets its own `BEGIN … COMMIT` only inside an `atomic = False` migration. `RunPython(..., atomic=False)` can't escape an `atomic = True` migration's transaction.
20. `CREATE INDEX CONCURRENTLY` and `DROP INDEX CONCURRENTLY` need `atomic = False`. Inside a transaction they fail with `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`, or `NotSupportedError` for `AddIndexConcurrently`.
21. Prefer `AddIndexConcurrently` / `RemoveIndexConcurrently` (`django.contrib.postgres.operations`) in an `atomic = False` migration; they handle partial indexes (`condition=`) and work with both drivers. For SQL Django can't generate, such as `IF NOT EXISTS`, use `SeparateDatabaseAndState` with `state_operations` that match the SQL exactly.
22. Send one `CONCURRENTLY` statement per `execute()`. On PostgreSQL, `RunSQL` passes a string to the server unsplit, and a multi-statement string runs as one implicit transaction, so two `CONCURRENTLY` statements in one string fail even with `atomic = False`. Pass `RunSQL` a list.
23. Never change autocommit in a migration; `atomic = False` already runs with it on, and neither driver needs an extra `commit()`. A helper that sets autocommit to `False` in `finally` leaves the shared connection in a transaction nothing commits, for the rest of that `migrate` run, in every app. Forward, that migration and every later one print `OK` and are rolled back at exit. Backward, a later `CONCURRENTLY` step fails and the exit rollback leaves migrations recorded whose objects are gone.
24. `IF NOT EXISTS` skips invalid indexes. A failed or cancelled concurrent build leaves `indisvalid = false`; the rerun prints `OK`, records the migration, and leaves an index queries can't use. After any failed build, check `indisvalid` and repair with `REINDEX INDEX CONCURRENTLY`, or drop and rebuild.
25. A concurrent build waits for open transactions in the same database that wrote to the table or hold a snapshot (such as `REPEATABLE READ`). Read-only `READ COMMITTED` sessions, writes to other tables and other databases don't block it. A `statement_timeout` that cancels the wait leaves an invalid index.
26. A migration that prints `OK` every run is not being recorded. Fix the cause, confirm its objects exist and its indexes are valid, then `migrate <app> <name> --fake`. `--fake` runs nothing; it only writes the row.

## Schema changes on busy tables

27. Start every atomic migration that alters a busy table with `migrations.RunSQL("SET LOCAL lock_timeout = '5s'", migrations.RunSQL.noop)`, and end it with `migrations.RunSQL(migrations.RunSQL.noop, "SET LOCAL lock_timeout = '5s'")` so the reverse run gets it too. When the lock isn't free, `migrate` exits with `django.db.utils.OperationalError: canceling statement due to lock timeout`, rolls everything back and records nothing; rerun it. Use `SET LOCAL`, never `SET`: a plain `SET` stays on the connection for the rest of the `migrate` run, and `SET LOCAL` does nothing in an `atomic = False` migration.
28. `AddField`, `AlterField`, `RemoveField`, `RenameField`, `RenameModel` and `AddConstraint` take `AccessExclusiveLock`, held until the migration commits. While `migrate` waits for it, every query on the table queues behind the migration. Keep `RunPython` backfills in their own migration: in the same atomic migration, the `AddField` lock blocked plain `SELECT`s for the whole backfill.
29. These rewrite the whole table and its indexes under `AccessExclusiveLock`: `IntegerField` to `BigIntegerField`, and a volatile `db_default` such as `RandomUUID()`. These don't: `default=`, `db_default` with a constant or `Now()`, widening a `varchar`, `varchar` to `text`; but an indexed `CharField` changed to `TextField` rebuilds its `_like` index inside the lock.
30. `default=uuid.uuid4`, like any callable default, is evaluated once for the existing rows: all 200,000 got the same UUID. Add the column nullable and backfill it.
31. Add a foreign key to a large table in three migrations: `SeparateDatabaseAndState` with `ADD CONSTRAINT ... NOT VALID`, then the index with `CONCURRENTLY` in an `atomic = False` migration, then `VALIDATE CONSTRAINT`, which takes only `ShareUpdateExclusiveLock`. A plain `AddField(ForeignKey)` also blocks inserts into the referenced table until commit, and removing a `ForeignKey` field locks both tables with `AccessExclusiveLock`.
32. `RenameModel` of a referenced model locks both tables and re-adds each child foreign key with a full validation. To rename only the Python class, keep the table: run `AlterModelTable` to the current table name first and keep `Meta.db_table`, and no SQL is sent.
33. Making a column `NOT NULL` without a long lock needs `NOT VALID` then `VALIDATE CONSTRAINT` in `RunSQL`. `ADD CONSTRAINT ... NOT NULL col NOT VALID` exists only from PostgreSQL 18; on 16 and 17 use `CHECK (col IS NOT NULL) NOT VALID`.

## Bulk operations

34. `bulk_create(update_conflicts=True, unique_fields=...)` can't target a partial unique constraint (`UniqueConstraint(condition=...)`): Django sends `ON CONFLICT("email")` with no predicate, and PostgreSQL raises `there is no unique or exclusion constraint matching the ON CONFLICT specification`. Use raw SQL with `ON CONFLICT (email) WHERE active DO UPDATE SET ...`, or `ignore_conflicts=True` for insert-if-missing.
35. Deduplicate objects on `unique_fields` before `bulk_create(update_conflicts=True)`: two rows with the same key in one batch fail with `ON CONFLICT DO UPDATE command cannot affect row a second time`.
36. After `bulk_create(ignore_conflicts=True)`, every object has `pk = None`, the inserted ones included. With `update_conflicts=True` every object gets a pk (the existing row's id on conflict), but only the pk is refreshed.
37. Set `batch_size` on `bulk_create()` yourself: with the default settings, 20,000 objects went out as one `INSERT`. More than one batch runs inside `BEGIN … COMMIT`, so a failing batch rolls back the earlier ones. Give `bulk_update()` a `batch_size` of 100 to 1,000: on 10k rows that was faster than one batch, and several times faster than a `save()` loop.
38. `bulk_update()`, `QuerySet.update()` and `save(update_fields=[...])` leave `auto_now` fields unchanged unless you include them; pass `updated_at=Now()` to `update()`.
39. Use `get_or_create()` only when the lookup fields have a unique constraint. Without one, two concurrent callers both insert, and later calls raise `MultipleObjectsReturned`. With one, the loser gets `created=False` and no exception, but inside `atomic()` it waits for the winner's whole transaction.
40. `QuerySet.delete()` runs its collecting `SELECT`s before `BEGIN`. When the child model has delete signal receivers, Django deletes the children by the ids it collected, so a child row inserted in between makes `COMMIT` fail with `update or delete on table "orders" violates foreign key constraint ... on table "order_lines"` (without receivers it deletes by parent id, and the new child goes too). Lock the parents with `select_for_update()` in the same `atomic()` first, or, on Django 6.1 and later, declare the child foreign key `on_delete=models.DB_CASCADE`.

## Debug procedure

### Transactions

1. See what PostgreSQL receives: on a local or test server, start PostgreSQL with `-c log_statement=all` and read its log. A write with no `COMMIT` after it is lost.
2. At the point in question: `connection.get_autocommit()`, `connection.in_atomic_block`, `connection.needs_rollback`.
3. Ask the driver: psycopg 3 `connection.connection.info.transaction_status` (`IDLE`, `INTRANS`, `INERROR`); psycopg2 `connection.connection.get_transaction_status()` (`0` idle, `2` in transaction, `3` in error).
4. Sessions holding a transaction open:
   `SELECT pid, state, xact_start, left(query, 60) FROM pg_stat_activity WHERE state LIKE 'idle in transaction%' ORDER BY xact_start;`

### Migrations

1. Compare `python manage.py showmigrations <app>` with `SELECT name, applied FROM django_migrations WHERE app = '<app>' ORDER BY name;`
2. Check the migration's objects exist and its indexes are valid:
   `SELECT c.relname, i.indisvalid FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid WHERE c.relname IN ('<index>');`
3. Look for autocommit changes: `grep -rn "set_autocommit\|connection.commit()" */migrations/`
4. If `migrate` hangs, find what it waits for: `SELECT pid, wait_event_type, wait_event, pg_blocking_pids(pid), left(query, 60) FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;`. The migration appears blocked by the session holding the table; every application query appears blocked by the migration.
5. Read the SQL with `python manage.py sqlmigrate <app> <name>`: atomic migrations are wrapped in `BEGIN;` … `COMMIT;`, and `RunPython` shows only `-- THIS OPERATION CANNOT BE WRITTEN AS SQL`, so read its code.
6. Before a concurrent build on a busy table, list `idle in transaction` sessions in that database (query above). During it, watch `SELECT phase, current_locker_pid, blocks_done, blocks_total FROM pg_stat_progress_create_index;`
